## Health Checks

Each service includes a lightweight HTTP health check server. By default, it listens on:
- Login Server: `30000`
- Char Server: `30100`
- Map Server: `30200`
- Node Server: `30000`

You can override the port using the `HEALTH_PORT` environment variable.

### Endpoints
- `GET /health`: Returns `200 OK` with `{ "status": "ok" }` if the service is healthy, or `503 Service Unavailable` with a reason if it's unhealthy.

### What each service checks

| Server | Checks |
|---|---|
| login | client listener, ISC listener, DB |
| character | client listener, ISC listener, **ISC client → login**, DB |
| map | **all per-map listeners**, **ISC client → character**, DB |

The ISC-client checks call `CRoseISC::is_connected()`, which is driven purely by the socket's
connect/disconnect callbacks. Do **not** switch these back to `is_active()`: that is a liveness flag
which `CRoseClient`'s constructor raises eagerly, so it reads healthy on a link that never connected
and stays healthy after a failed TLS handshake.

### Kubernetes Compatibility
These endpoints are suitable for Liveness and Readiness probes:
```yaml
livenessProbe:
  httpGet:
    path: /health
    port: 30000
readinessProbe:
  httpGet:
    path: /health
    port: 30000
```

## C++ Installation - Unix

### Unix software required
![gpp]
![libmysql]
[![cmake]][cmake-link]
[![python]][python-link]

If you get the source from github, you need to setup the build environment:

```cmd
    git submodule update --init --recursive
    mkdir build
    cd build
    cmake ..
```

Note, you may need to install the following packages depending on your OS:

```cmd
    unzip
    autoconf
    libtool
    libssl-dev
    libncurses5-dev
    libreadline-dev
    libcurl4-openssl-dev
    libsqlite3-dev
    libmysqlclient-dev
```

To build the servers, execute the following:

```cmd
    make
```

To install the servers to the system (not recommended), execute the following commands:

```cmd
    make install
```

"make install" may require superuser privileges.

If you installed the servers, to run the servers execute the following:

```cmd
    LoginServer&
    CharServer&
    MapServer&
```

If you opted to keep them in place, the server binaries are located in the bin folder inside the build directory. So from where you ran the command make, you will want to run the following:

```cmd
    ./bin/LoginServer&
    ./bin/CharServer&
    ./bin/MapServer&
```

After running for the first time, the servers will create a config file in the current directory that you need to edit.

## Server Configuration

The servers can be configured using a `server.json` file. This file is automatically generated if any
server is started and no `server.json` file exists. It's recommended to generate this file before
continuing with the project setup. Simply start any of the servers to generate the file.

`config/server.example.json` is a committed reference copy showing every key, including the `ssl`
block described below. Note that the file is parsed as **strict JSON** — comments are not allowed.

## TLS Certificates (Docker)

The Docker images are built with `-DENABLE_SSL=ON`, and `ENABLE_SSL` is a **compile-time** switch
with no runtime off-ramp: a TLS build refuses to `listen()` without a usable certificate and key, so
the login, character and map servers will not start at all until one exists.

The compose stack provisions one from Let's Encrypt with a `certbot` service, using a **DNS-01**
challenge — the game protocol is a custom binary one and there is no web server in the stack to
answer an HTTP-01 challenge.

### Setup

1. Fill in the ACME settings in `.env`:

   ```
   ACME_DOMAIN=rose.example.com
   ACME_EMAIL=you@example.com
   ACME_STAGING=1
   ACME_DNS_PLUGIN=cloudflare
   ACME_DNS_IMAGE=certbot/dns-cloudflare:latest
   ```

   `ACME_DOMAIN` accepts several space-separated names; they land on one certificate as SANs and the
   first names the lineage.

2. Create the DNS credentials:

   ```sh
   cp secrets/dns.ini.example secrets/dns.ini
   chmod 600 secrets/dns.ini      # certbot rejects a group/world-readable file
   ```

   For Cloudflare this is a scoped API token with `Zone / DNS / Edit` on the one zone — not the
   global API key. To use a different provider, change `ACME_DNS_PLUGIN` and `ACME_DNS_IMAGE`
   together; any `certbot/dns-*` image works. Route53 takes no credentials file — delete
   `secrets/dns.ini` and put the `AWS_*` variables in `.env` instead.

3. Set `ssl.sniHostname` in `config/server.json` to match the first name in `ACME_DOMAIN`. This is
   required, not cosmetic: the inter-server (ISC) links dial the compose service names `login` and
   `character`, which no Let's Encrypt certificate covers, so peer verification rejects every
   inter-server handshake without the override. The `certificateChainFile` and `privateKeyFile`
   paths need no editing — they point at the fixed location the certbot service publishes to.

4. Bring the stack up. `certbot` obtains the certificate first; the game servers gate on its
   healthcheck, which waits for both PEM files to appear.

   ```sh
   docker compose up -d
   docker compose logs -f certbot
   ```

5. Once a staging certificate issues cleanly, switch to production:

   ```sh
   # blank ACME_STAGING in .env, then discard the staging lineage
   docker compose exec certbot rm -rf /etc/letsencrypt/live /etc/letsencrypt/archive /etc/letsencrypt/renewal
   docker compose restart certbot
   ```

   Staging is the default because Let's Encrypt production enforces a hard limit of five failures per
   account per hostname per hour, and a misconfiguration burns through it quickly.

### Renewal

The certbot container checks for renewal every `ACME_RENEW_INTERVAL` (default 12h). Because the
servers load the certificate once while building the SSL context at listener setup, and there is no
reload path (no SIGHUP handler), a renewal **restarts `osirose-login`, `osirose-character` and
`osirose-map`** in that order via its deploy hook. Verify the whole path without waiting 60 days:

```sh
docker compose exec certbot certbot renew --dry-run
```

> **Security note:** the certbot service mounts `/var/run/docker.sock` so that its deploy hook can
> restart the game containers. That grants it root-equivalent control of the host. To avoid it, put
> `tecnativa/docker-socket-proxy` in front of the socket with only `CONTAINERS=1 POST=1`, or drop
> the mount and restart the stack from the host instead. `secrets/dns.ini` also holds a live DNS API
> token — scope it to the single zone and keep it out of version control.

### Ports

The client-facing ports (`29000`, `29100`, `29200-29300`) are published to the host. The ISC ports
(`29010`, `29110`) are server-to-server only and are **not** published; services reach each other by
name on the compose network.

## Auto-Recovery (Docker)

Docker marks a container unhealthy but never restarts it, and `depends_on: service_healthy` only
gates startup — so the stack runs an `autoheal` service that restarts any container labelled
`autoheal=true` once its health check fails. Login, character and map carry that label.

```sh
docker compose logs -f autoheal      # watch restarts as they happen
```

Tunables live in the `autoheal` service: `AUTOHEAL_INTERVAL` (poll seconds),
`AUTOHEAL_START_PERIOD` (grace period after autoheal itself starts), and
`AUTOHEAL_DEFAULT_STOP_TIMEOUT`. That last one matters because MapServer does not act on `SIGTERM`
— it has to be `SIGKILL`ed, so every restart costs the full timeout.

Note the deliberate cascade: character aborts at startup if it cannot reach login's ISC port, and
map aborts if it cannot reach character. If login stays down, the servers below it will restart in a
loop until it returns. That is intended — a TLS build cannot serve without those links, so failing
loudly beats running in a half-dead state.

> **Security note:** autoheal mounts `/var/run/docker.sock`, the same root-equivalent exposure
> described for certbot above. The same `docker-socket-proxy` hardening applies to both.

## Client Setup

The server is designed to work with the assets from the `ROSE_112_112NA` client. Using different
assets may cause issues due to incompatibility. The client is available to download
[here](https://mega.nz/#F!8AkG3TzJ!6eoMc65tHmF_d_6nAvf8ZA?UQc3zZKb).

Run the installer and install the game to a desired location. While this project uses the assets
from that client it does not use the binaries. For full compatibility you will need to download
the latest client binaries from the project's [Releases Page](https://github.com/dev-osrose/osIROSE-new/releases)

> 12/5/2019 - Until a new client release is up on github you'll need to use the client from discord: [SHA256 Client](https://cdn.discordapp.com/attachments/454345032846016519/625869971284557824/sha256_client_release_fixed.zip)

After downloading the client files, copy them to the `ROSE_112_112NA` installation directory (default:
`C:\Program Files (x86)\TriggerSoft\Rose Online`) and overwrite the existing files.

 Connecting to the server requires using a special command from the command line, like so:

`trose.exe @TRIGGER_SOFT@ _server 127.0.0.1` (replace the IP if not running locally

For convenience, this command can be saved to a file with the extension `.cmd` in the same folder
as `trose.exe`. Then, the game can be launched by double clicking this file.

## Database Setup

The server requires a [MySQL](https://mysql.com/) (or [MariaDB](https://mariadb.com/)) database server.

To setup the database, first create a new database (e.g. `osirose`). You will then need to execute the
`Database/osirose.sql` script to generate the database schema and the `Database/item_db.sql` to
populate the item database. This can be done using a database tool or from the command line like so:
```cmd
  mysql -u<user> -p<password> <database_name> < Database/osirose.sql
  mysql -u<user> -p<password> <database_name> < Database/item_db.sql
```

**NOTE**: The item table was generated using client v112_112na. If you are using a different client,
please generate your own table to match the information you need.

After setting up the database, two special users need to be created for the login and character
servers. They can be created by executing the following SQL commands:

```sql
  call create_account("login", "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08");
  call create_account("char", "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08");
  update accounts set account_type="system" where username="login";
  update accounts set account_type="system" where username="char";
```

The value `9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08` is an SHA256 hash of the default server passwords created
in the default `server.json` file. It should match the following sections:

```json
    ...
    "charServer":  {
        ...
        "loginUser":         "login",
        "loginPassword":     "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08",
        ...
    },
    "mapServer":   {
        ...
        "charUser":     "char",
        "charPassword": "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08",
        ...
    },
    ...
```

To use your own password, generate an [SHA256 hash](https://emn178.github.io/online-tools/sha256.html) of your password
and update the accounts database and the `server.json` file.

Finally, we need to create an account to join the game with. Run the `create_account` procedure
again to create a user account, for example:

```sql
  call create_account("admin", "8c6976e5b5410415bde908bd4dee15dfb167a9c873fc4bb8a81f6f2ab448a918") # Password is admin
```

Alternatively, automatic account creation can be enabled in the server config. This will automatically
create an account if a user attempts to login to an account that exist. This is recommended as it is
much more convenient than having to create password hashes and running sql commands. Simply, try to
log in, fail, then try to login again with the same credentials!

To enable it modify `server.json` to enable `createAccountOnFail`:
```json
  "loginServer": {
      "createAccountOnFail": true,
      ...
  },
```
